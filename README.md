# Z69: сборка приложения и проверка лабораторных работ

Это руководство предназначено для студента, который запускает готовый `Z69.exe`, и для преподавателя, который собирает приложение из исходного кода. Здесь описаны оба модуля приложения — **GNS3** и **Docker**: команды, допустимые значения, порядок самостоятельной проверки и типичные ошибки запуска.

> 🔴 **Главное правило:** сначала проверьте свою работу обычными средствами GNS3 или Docker, затем запускайте Z69. Чекер не исправляет проект и не заменяет отладку — он запускает работу, проверяет наблюдаемый результат и показывает, какой критерий не выполнен.

Работа должна быть воспроизводимой: корректно запускаться после переноса на другой компьютер, пересборки и изменения предусмотренных заданием входных данных. Жёстко записанные ответы, зависимость от посторонних локальных файлов, вмешательство в Z69 или подмена окружения не считаются выполнением лабораторной и могут потребовать повторной ручной проверки.

## 1. Сборка и запуск Z69

### Если вам выдали готовое приложение

Запустите `Z69.exe`. Обычно он находится в папке `dist`. Перед проверкой Docker отдельно запустите Docker Desktop; перед проверкой GNS3 запустите GNS3 и откройте нужный проект.

### Если приложение нужно собрать

1. Установите Python и убедитесь, что команда ниже выводит номер версии:

   ```powershell
   python --version
   ```

2. В корне проекта запустите `install_deps.bat`. Права администратора нужны только в случае ошибки доступа при установке библиотек.

3. Для проверки без сборки можно выполнить:

   ```powershell
   python main_ui.py
   ```

4. Для создания одного исполняемого файла выполните:

   ```powershell
   python build.py
   ```

5. Готовый файл появится по пути `dist\Z69.exe`.

Если команда `python` не найдена, переустановите Python с включённой опцией **Add Python to PATH** или попробуйте команду `py` вместо `python`.

## 2. Установка Docker Desktop и WSL 2

Docker-модуль подключается к локальному Docker Engine. Одной установки недостаточно: во время проверки Docker Desktop должен быть запущен и показывать состояние **Engine running**.

### Основной способ для современных Windows 10/11

1. Откройте PowerShell от имени администратора и выполните:

   ```powershell
   wsl --install
   ```

2. Перезагрузите компьютер.

3. Проверьте WSL:

   ```powershell
   wsl --status
   wsl -l -v
   ```

   В столбце `VERSION` должна быть указана версия `2`.

4. Установите Docker Desktop с [официальной страницы Docker](https://docs.docker.com/desktop/setup/install/windows-install/). При выборе движка используйте WSL 2.

5. Запустите Docker Desktop и дождитесь **Engine running**.

6. Откройте PowerShell и выполните:

   ```powershell
   docker version
   docker info
   docker compose version
   ```

   `docker version` должен показать секции Client и Server, `docker info` — сведения о локальном Engine, а последняя команда — версию Compose.

Официальная инструкция Microsoft по WSL: [Install WSL](https://learn.microsoft.com/windows/wsl/install).

### Если `wsl --install` не работает

В PowerShell от имени администратора включите компоненты вручную:

```powershell
dism.exe /online /enable-feature /featurename:Microsoft-Windows-Subsystem-Linux /all /norestart
dism.exe /online /enable-feature /featurename:VirtualMachinePlatform /all /norestart
```

Перезагрузите компьютер, затем выполните:

```powershell
wsl --update
wsl --set-default-version 2
```

Если WSL сообщает, что виртуализация недоступна, включите Intel VT-x/AMD-V в BIOS/UEFI. На учебном компьютере для этого может потребоваться помощь администратора.

## 3. Интерфейс приложения

В левой панели находятся три кнопки:

1. **Иконка GNS3** — открыть или закрыть консоль модуля GNS3.
2. **Иконка Docker** — открыть или закрыть консоль модуля Docker.
3. **Иконка папки** — выбрать папку работы **только для Docker**. Для GNS3 эта кнопка не используется.

Команду вводят в нижней строке чёрной консоли и подтверждают клавишей Enter. Повторное нажатие на активную иконку либо крестик внутри консоли скрывает её. Верхнюю чёрную полосу консоли можно перетаскивать мышью.

В Docker-консоли:

- белые строки — обычная информация и успешные пункты `[PASSED]`;
- красные строки — ошибки и пункты `[FAILED]`;
- голубая строка — выполняющаяся проверка;
- зелёная заполненная шкала — завершение этапа, но не обязательно успешное прохождение всей работы.

## 4. Быстрый старт: GNS3

Перед запуском сохраните проект GNS3. Во время проверки приложение взаимодействует с проектом автоматически; не редактируйте топологию до завершения операции.

### Команды GNS3

| Команда | Что делает | Пример |
|---|---|---|
| `help` | Показывает все команды | `help` |
| `show` | Показывает текущие настройки; пароль выводится звёздочками | `show` |
| `ip <адрес>` | Задаёт IPv4-адрес сервера GNS3 | `ip 192.168.56.101` |
| `port <порт>` | Задаёт порт GNS3 Server, допустимо `1`–`65535` | `port 3080` |
| `proj <имя>` | Задаёт точное имя проекта в GNS3 | `proj Лабораторная 1` |
| `lab <номер>` | Выбирает лабораторную работу | `lab 1` |
| `login <имя>` | Логин Telnet для QEMU/MikroTik | `login admin` |
| `pass <пароль>` | Пароль Telnet для QEMU/MikroTik | `pass student123` |
| `test` | Проверяет доступность API GNS3 | `test` |
| `run` | Запускает проверку с текущими настройками | `run` |

Поддерживаемые работы в проекте: `1`, `2_1`, `2_2`, `2_3`, `3_1`, `3_2`, `4`, `5`, `6`.

### Последовательность запуска

```text
ip 192.168.56.101
port 3080
proj точное имя проекта
lab 1
login admin
pass *ваш_пароль*
show
test
run
```

Нормальный результат команды `test` начинается с `OK:` и содержит адрес сервера. Команду `run` запускайте только после успешного `test`.

## 5. Быстрый старт: Docker

### Команды Docker-модуля

| Команда | Что делает | Пример |
|---|---|---|
| `help` | Показывает команды | `help` |
| `show` | Показывает выбранную папку и лабораторную | `show` |
| `proj <путь>` | Задаёт папку с работой | `proj C:\Users\Student\Desktop\lab10` |
| `lab <имя>` | Выбирает чекер `lab10`–`lab14` | `lab lab10` |
| `check` | Запускает проверку выбранной папки | `check` |

Чекеры есть только для `lab10`, `lab11`, `lab12`, `lab13` и `lab14`. Материалы lab15–16 могут находиться в проекте, но текущая версия приложения их не проверяет.

### Последовательность запуска

1. Запустите Docker Desktop и дождитесь **Engine running**.
2. Нажмите иконку папки и выберите корневую папку своей работы.
3. Откройте Docker-консоль.
4. Выполните:

   ```text
   lab lab10
   show
   check
   ```

Вместо кнопки папки можно использовать `proj C:\полный\путь`. В консоли Z69 путь с пробелами вводите целиком без кавычек.

После проверки найдите итоговые строки `Total`, `Passed`, `Failed` и `Success Rate`. Работа прошла полностью только тогда, когда `Failed: 0` и `Success Rate: 100.0%`.

## 6. Как подготовить проект GNS3

1. Запустите GNS3 Server и GNS3 GUI.
2. Откройте нужный проект и сохраните его.
3. Проверьте, что имя проекта в `proj` совпадает символ в символ с именем в GNS3.
4. Запустите каждый узел вручную хотя бы один раз.
5. Откройте консоли устройств и убедитесь, что они отвечают.
6. Для MikroTik/QEMU проверьте логин и пароль вручную. Консоль должна показывать запросы `Login:` и `Password:`, а после входа — приглашение командной строки.
7. Для VPCS выполните `show ip` и убедитесь, что адрес уже получен либо доступен DHCP.
8. Для контейнерных узлов проверьте, что их консоли и сетевые интерфейсы доступны после запуска проекта.
9. Остановите ручную отладку, выполните в Z69 `show`, затем `test`, затем `run`.

Не меняйте топологию во время проверки и не запускайте вторую проверку параллельно. Дождитесь итогового сообщения приложения.

## 7. Как читать результат GNS3

Во время работы приложение показывает этапы выполнения. Дождитесь итогового результата и не закрывайте GNS3 или Z69 раньше времени.

Если проверка завершилась неуспешно, используйте сообщение как указание на область, которую нужно перепроверить: доступность проекта, запуск устройств, адресацию, маршрутизацию, службы или учётные данные. Исправляйте сам проект в соответствии с заданием, а не пытайтесь подстроить отдельный вывод под сообщение приложения.

Если формулировки недостаточно для самостоятельной диагностики, сохраните снимок консоли и обратитесь к преподавателю.

## 8. Если GNS3 не работает

### `test` сообщает `Failed to connect to GNS3 server`

Проверьте по порядку:

1. GNS3 запущен.
2. В `ip` указан адрес именно GNS3 Server, а не адрес роутера из топологии.
3. Порт совпадает с настройками сервера. Часто используется `3080`, но в удалённой учебной среде может быть `80`.
4. Адрес открывается с компьютера студента и не блокируется VPN, прокси или брандмауэром.
5. Повторите `show`, исправьте `ip`/`port` и снова выполните `test`.

### `Project ... not found`

Команда `proj` принимает имя, а не путь к файлу. Скопируйте имя проекта из GNS3 без сокращений. Проверьте пробелы, дефисы и регистр.

### Узел не запускается или отсутствует в результате

Откройте проект в GNS3 и запустите проблемный узел вручную. Проверьте его тип, имя, шаблон и консольный порт. Если устройство переименовано относительно задания, верните требуемое имя.

### Ошибка входа в MikroTik или долгое ожидание QEMU

Войдите в консоль этого роутера вручную. Затем исправьте `login` и `pass`. Не указывайте звёздочки, которые показывает команда `show`: это только маскировка пароля.

### VPCS не получил адрес

Проверьте DHCP-сервер, соединения и состояние интерфейсов. В консоли VPCS выполните `ip dhcp`, затем `show ip`. Адрес должен выдаваться стабильно и без ручного вмешательства во время проверки.

### После проверки проект остановился и закрылся

Это штатное поведение текущего модуля. Перед `run` сохраните все изменения. После проверки снова откройте проект, если хотите продолжить работу.

# 🔴 Подробное руководство по модулю Docker

## 9. Перед проверкой Docker

Z69 использует установленный на компьютере Docker. Во время проверки могут выполняться сборка и запуск проекта, поэтому Docker Desktop и интернет для загрузки отсутствующих образов должны быть доступны. Не закрывайте Z69 и Docker Desktop до появления итоговой статистики и не запускайте несколько проверок одновременно.

Содержимое проверки не раскрывается. Приложение оценивает работу как законченную лабораторную, а не как набор строк, файлов или специально подготовленных ответов. Проект должен выполнять задание полностью как при обычном ручном запуске.

## 10. Общая самостоятельная проверка Docker-проекта

В PowerShell перейдите в папку работы и последовательно выполните:

```powershell
docker info
docker compose config
docker compose up -d --build
docker compose ps
docker compose logs --tail 100
docker compose down
```

Если работа не использует Compose, выполните:

```powershell
docker build -t my-lab-test .
docker run --rm my-lab-test
```

Сначала исправьте ошибки этих команд. Z69 использует тот же Docker Engine, поэтому сломанная ручная сборка не пройдёт чекер.

Корнем работы считается папка, которую вы выбрали кнопкой или командой `proj`. Не выбирайте родительскую папку, если `Dockerfile` или Compose-файл лежит уровнем ниже.

## 11. Что студент должен проверить перед сдачей

Ниже приведён не алгоритм Z69, а минимальный порядок самопроверки полноценной работы. Полные требования находятся в задании соответствующей лабораторной.

### lab10 — веб-приложение с температурами

В корне работы должен находиться `Dockerfile`. Соберите образ вручную, запустите контейнер и откройте приложение так, как требуется в задании.

Убедитесь, что приложение действительно получает и отображает необходимые данные о погоде для всех указанных в задании городов, корректно работает после повторного запуска и не зависит от файлов или программ вне переданного проекта. Статическая страница, заранее записанные ответы и вывод, созданный только для прохождения проверки, не являются выполненной лабораторной работой.

### lab11 — Python-программа времени и архитектуры

В корне работы должны находиться файлы, предусмотренные заданием, включая `Dockerfile` и программу. Соберите образ и запустите его несколько раз с обычными и изменёнными параметрами окружения.

Проверьте, что программа самостоятельно определяет архитектуру, выводит актуальное время с требуемым заданием интервалом, реагирует на предусмотренные переменные окружения, продолжает работать без исключений и сразу показывает новые сообщения в логах. Не подменяйте вычисления фиксированными значениями: работа должна оставаться корректной при другом окружении запуска.

### lab12 — Compose, приложение lab11, Prometheus и Grafana

В корне работы должен находиться Compose-файл. Команда `docker compose config` должна выполняться без ошибок.

Запустите весь проект через Compose и убедитесь, что программа из предыдущей работы, Prometheus и Grafana действительно работают вместе. Проверьте состояние контейнеров, логи, доступность веб-интерфейсов и корректную остановку проекта. Наличие записей в YAML без работающих сервисов не считается выполнением.

### lab13 — сети и мониторинг MongoDB

Соберите инфраструктуру из MongoDB, экспортера метрик, Prometheus и Grafana в соответствии со схемой лабораторной. Разделите сервисы по требуемым сетям и используйте штатное обнаружение сервисов Docker вместо фиксированных адресов контейнеров.

После запуска убедитесь, что контейнеры работают стабильно, exporter получает данные из MongoDB, Prometheus принимает настоящие метрики, а Grafana использует Prometheus как источник данных. Проверьте это через интерфейсы самих приложений и логи. Четыре независимо запущенных контейнера без рабочего пути данных не являются готовой системой.

### lab14 — оптимизация и компиляция C-программы

В корне работы должны находиться `Dockerfile`, исходный файл `hello.c` и остальные файлы, предусмотренные заданием. Контейнер должен компилировать переданный исходный код, запускать полученную программу и передавать требуемый результат на хост.

Проверьте работу после изменения текста программы в `hello.c`: результат должен измениться после новой сборки. Заранее созданный `out.txt`, жёстко записанный текст или двоичный файл вместо реальной компиляции не являются выполнением задания.

Если по заданию требуется сравнить исходный и оптимизированный варианты, оба варианта должны сохранять одинаковое полезное поведение, а оптимизация должна быть подтверждена обычными командами Docker. Используйте `.dockerignore`, разумные слои и многоступенчатую сборку там, где это оправдано.

## 12. Если Docker-проверка не работает

### `Failed to connect to Docker`, `docker daemon` или `pipe/docker_engine`

Docker Desktop не запущен либо Engine ещё загружается. Откройте Docker Desktop, дождитесь **Engine running**, выполните `docker info` и повторите `check`.

### `Please set a valid Docker project folder`

Нажмите иконку папки или выполните `proj <путь>`, затем `show`. После перезапуска готового однофайлового приложения путь лучше выбирать заново.

### `Dockerfile не найден в корне проекта`

Выбрана не та папка. Выбирайте каталог, внутри которого непосредственно виден файл `Dockerfile`. Имя чувствительно к написанию: нужен именно `Dockerfile`, без `.txt`.

### Compose-файл не найден

Для lab12 и lab13 допустимы только имена:

```text
compose.yaml
compose.yml
docker-compose.yaml
docker-compose.yml
```

Проверьте, что Windows не скрыла расширение и файл не называется, например, `docker-compose.yml.txt`.

### `docker compose config` сообщает ошибку YAML

YAML чувствителен к отступам и табуляции. Используйте пробелы, выровняйте вложенные секции и снова выполните `docker compose config` вручную. Исправлять нужно первую показанную ошибку: последующие часто являются её следствием.

### Ошибка сборки образа

Запустите `docker build .` или `docker compose build` в папке работы и прочитайте последние строки. Частые причины: неверный путь в `COPY`, отсутствующий файл, недоступный базовый образ, ошибка команды `RUN`, отсутствие интернета или опечатка в Dockerfile.

### Контейнер сразу завершился

Выполните `docker compose ps -a` и `docker compose logs --tail 100`. Для одиночного контейнера используйте `docker ps -a`, затем `docker logs <имя_или_id>`. Исправьте команду запуска или исключение приложения.

### Порт уже занят

Остановите свою предыдущую копию проекта:

```powershell
docker compose down
docker ps
```

Если порт занят другой программой, закройте её или измените внешний порт. Внутренний порт сервиса должен остаться тем, который ожидает приложение.

### Prometheus или Grafana ещё не готовы

Проверьте `docker compose ps` и логи конкретного сервиса. Контейнер со статусом `running` ещё не гарантирует готовность API. Убедитесь, что конфигурационные файлы примонтированы по правильным путям и что опубликованы нужные порты.

### Prometheus не получает метрики

Откройте интерфейс Prometheus и изучите состояние источников и текст последней ошибки. Проверьте сетевую доступность exporter из контейнера Prometheus и соответствие конфигурации заданию. Не заменяйте исправление соединения заранее подготовленными данными.

### Grafana не видит Prometheus

Проверьте источник данных Grafana и сетевую доступность Prometheus из контейнера Grafana. Помните, что `localhost` внутри контейнера указывает на этот же контейнер, а не на соседний сервис.

### Проверка зависла или идёт долго

Первая сборка может скачивать большие образы. Посмотрите активность Docker Desktop и наличие интернета. Не запускайте второй `check` параллельно. Если несколько минут нет ни сетевой, ни дисковой активности, остановите старые контейнеры своей работы, перезапустите Docker Desktop и повторите проверку один раз.

### Есть `[FAILED]`, хотя приложение «открывается»

Читайте название конкретного пункта и повторите полную ручную проверку по заданию. Статус `running`, открывшаяся страница или наличие нужного файла ещё не доказывают корректность всей лабораторной. Исправляйте причину сбоя, а не добавляйте специальные ответы только для Z69.
